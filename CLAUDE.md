# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CtrlAgent turns a game controller into a two-way control surface for AI coding agents: controller inputs become agent commands (submit, interrupt, approve, decline, switch session), and agent lifecycle events come back as distinct rumble patterns. Both sides are deliberately pluggable — controllers via `IControllerDevice` (today: Xbox-family/XInput, Elite Series 2 paddles via the GameInput bridge, and PS5 DualSense/Edge over raw HID; next: generic pads), agents via `IAgentAdapter` (today: Codex and Claude Code; planned: Cursor, Google Antigravity). The product direction is all popular controllers × all popular agentic platforms — don't frame it as Xbox- or single-agent-specific. Windows-first, pre-alpha MVP.

## Build and test

The SDK is pinned to .NET 10 `10.0.302` via `global.json` (rolls forward within .NET 10). All managed projects share `Directory.Build.props`: `net10.0`, C# 14, nullable enabled, **warnings as errors** (the tree is warning-free — keep it so rather than suppressing).

```powershell
dotnet restore CtrlAgent.sln
dotnet build CtrlAgent.sln --configuration Release
dotnet run --project tests/CtrlAgent.Tests/CtrlAgent.Tests.csproj --configuration Release
```

Tests are a deliberately dependency-free console harness (no xUnit/NUnit): `tests/CtrlAgent.Tests/Program.cs` holds a `(Name, Func<Task>)` array, prints `PASS`/`FAIL` per test, and exits nonzero on any failure. There is no filter mechanism — to run a single test, temporarily trim the array; to add a test, append a tuple and a local static function.

The native GameInput bridge is a separate C++ project (not in the .sln) and needs MSBuild from a Visual Studio developer shell:

```powershell
msbuild native/CtrlAgent.GameInputBridge/CtrlAgent.GameInputBridge.vcxproj /restore /m /p:Configuration=Release /p:Platform=x64
```

It pins `Microsoft.GameInput` 3.4.x (`GameInputPackageVersion` in the .vcxproj) and compiles against the package-selected `GAMEINPUT_API_VERSION`. CI (`.github/workflows/ci.yml`) runs both halves on `windows-latest` and uploads build logs as artifacts. Releases (`.github/workflows/release.yml`) publish a portable self-contained zip and an Inno Setup installer (`installer/CtrlAgent.iss` — per-user default, Start Menu + optional desktop/startup shortcuts). Trigger by pushing a `v*` tag **or** via `workflow_dispatch` with a `version` input (the workflow creates the tag/release itself; both paths resolve `RELEASE_VERSION`).

Run the app end-to-end without real agent risk: `dotnet run --project src/CtrlAgent.App/CtrlAgent.App.csproj -- --agent mock` (or `--agent codex --cwd <repo>`). `src/CtrlAgent.Demo` plays the haptic patterns standalone. `--validate` runs the guided hardware wizard (`ValidationWizard` in the App; report model/gates in Core's `Validation.cs`) and writes `validation/<date>-elite-series-2-<transport>.md`.

## Architecture

Two directions flow through the same pipeline (see `docs/architecture.md`):

- **Control path:** controller adapter → normalized `ControllerInputEvent` → `MappingEngine` → `AgentCommand` → `IAgentAdapter.ExecuteAsync`.
- **Feedback path:** `IAgentAdapter.ReadEventsAsync` → normalized `AgentEvent` → `FeedbackRouter` → `HapticPattern` → `HapticScheduler` → `IControllerDevice.PlayAsync`.

Project boundaries:

- `src/CtrlAgent.Core` — all contracts (`IControllerDevice`, `IAgentAdapter`, events, commands), `MappingEngine`, profile validation/JSON (`Profiles.cs`), `FeedbackRouter`, `HapticPatternCatalog`, `HapticScheduler`. **Must stay platform-independent: no references to GameInput, XInput, Codex, UI frameworks, or keyboard injection** (System.Text.Json is fine — it's BCL).
- `src/CtrlAgent.Platform.Windows` — `WindowsControllerProvider` resolves in order: native GameInput bridge → DualSense over raw HID (`DualSenseControllerDevice` + SetupAPI/hid.dll P/Invoke in `DualSenseHidNative.cs`) → XInput fallback (`XInputNative.cs`). Bridge path resolution order: `--gameinput-bridge` argument → `CTRL_AGENT_GAMEINPUT_BRIDGE` env var → `CtrlAgent.GameInputBridge.exe` beside the app.
- `src/CtrlAgent.Controllers.DualSense` — the pure DualSense wire protocol (input report parsing for USB 0x01/Bluetooth 0x31, output report building with rumble/lightbar/adaptive-trigger effects, Bluetooth CRC32). A pattern's trigger channels become continuous trigger resistance (`DualSenseTriggerEffect`) — the pull physically stiffens while an approval is pending. No OS calls, fully unit-tested; keep HID I/O out of it. Cross→A/Circle→B/Square→X/Triangle→Y positional mapping; Edge paddles/Fn → the four paddle controls. Byte layout is community-documented and unverified on real hardware.
- `native/CtrlAgent.GameInputBridge` — C++ console exe the managed host spawns; talks newline-delimited JSON over stdio (emits `ready` and input events; accepts `{"type":"rumble", ...}`). This is the trigger-rumble path and the intended paddle path — but hardware validation (2026-07-24) showed the PC GameInput redistributable never reports Elite Series 2 paddles (unmapped paddles are silent; mapped ones arrive as face buttons) and does not enumerate Bluetooth Xbox controllers at all, so the bridge reports `hasFourPaddles: false` and paddle support is experimental pending a raw-report path (see `docs/controller-validation.md`).
- `src/CtrlAgent.Adapters.Mock` / `src/CtrlAgent.Adapters.Codex` / `src/CtrlAgent.Adapters.ClaudeCode` — `IAgentAdapter` implementations. The Codex adapter spawns `codex app-server` and speaks JSON-RPC-style JSONL over stdio; classification lives in the pure, unit-tested `CodexProtocolParser` (the adapter keeps only what needs live state — current thread/turn and outstanding requests). On app-server crash it fails in-flight requests, publishes an Error event, and restarts with capped backoff (max 5 attempts), then resumes the previously active thread via `thread/resume` (fresh thread on failure); thread switching also issues `thread/resume` so pre-crash threads reload from disk; while down, `ExecuteAsync` publishes an Error event instead of throwing. The Claude Code adapter spawns `claude --print --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --include-partial-messages`; it streams partial text as rolling Working snapshots (throttled to 250 ms), surfaces concrete tool detail (`Bash: npm test`, `TodoWrite` → `Plan 2/5 — …`), tool results (`→ output snippet`, `→ ⚠ …` on error), a "Thinking…" state, the session's model/MCP status/slash-command list on init, and turn stats (duration/turns/cost) on results; approvals render concretely (`Claude Code wants: Write: src/App.cs`) and approve-for-session echoes the CLI's `permission_suggestions` when present — `HostEngine` dedups repeated Working events so the log and rumble see one state change while UIs get every snapshot; line classification lives in the pure `ClaudeStreamParser` (unit-tested), `can_use_tool` control requests become ApprovalRequired events answered with allow/deny control responses (allow echoes the tool input as `updatedInput`), `SetPermissionMode` sends `set_permission_mode` control requests (default/plan/acceptEdits/auto/dontAsk — `bypassPermissions` is excluded because a live session rejects it unless launched with `--dangerously-skip-permissions`; a turn ended by our own interrupt is republished as Completed "Turn interrupted." rather than the Error the CLI reports it as; wire shapes in the unit-tested `ClaudeControlRequest`), NewSession restarts the process, Next/PreviousSession restart it with `--resume <session-id>` to cycle known sessions, `ResumeSession` restarts with a caller-supplied id the same way (the id may come straight from Claude Code's on-disk store — `ClaudeSessionCatalog` in the adapter project reads it for UIs: id from the file name, title from a summary line or first prompt), and crash restart resumes the live session the same way. The Claude adapter is swept live against CLI 2.1.220 (init, streaming turns, approve/deny/**approve-for-session**, interrupt, all five permission modes, model, compact, crash restart); **`system/init` arrives every turn, so the ready banner is published only when the session id changes**. Session cycling cannot be verified from inside a Claude Code session — a nested CLI reports the outer session's id for every session. The Codex adapter still needs live verification. Bare CLI names resolve through PATH/PATHEXT via `AgentExecutableResolver` (Core) — `Process.Start` on Windows does not.
- `src/CtrlAgent.Presentation` — GUI decision-making with **no UI framework in it**: `TranscriptFolder` (how agent events fold into conversation rows — streamed prose updates one bubble, non-prose closes it, an approval deliberately does not), `ActivityText`, `LogClassifier` (severity, checked most-severe first so "Approval declined" reads as an error), `ApprovalControls`, `MarkdownLite` (the small markdown dialect agent prose uses — bold/italic/inline code/fences/bullets/headings — parsed into blocks; unrecognized syntax stays literal), `UnifiedDiffParser`/`WorkspaceDiff` (the diff review panel's brain: parse `git diff` output into files/hunks/lines, collect `git diff HEAD` plus untracked files folded in as synthetic all-added diffs — runs the user's own git so the answer matches their `git status`; errors are returned readable, never thrown). It exists because `CtrlAgent.Gui` targets `net10.0-windows` and the `net10.0` test project cannot reference it — this logic used to fall between the two harnesses and was untested. Keep Avalonia out of it.
- `src/CtrlAgent.Hosting` — the shared `HostEngine` both hosts build on (it also resolves `CycleModel`/`CycleEffort` into concrete `SetModel`/`SetEffort` in `ResolveCycle` and tracks model/effort/permission-mode in `Settings`, raising `SessionSettingsChanged` — cycle position and the current mode live here, once, so adapters never track them and no UI keeps a private copy that desyncs when a controller binding moves the same knob) (references Core only; hosts inject `IControllerProvider`/`IAgentAdapter` and the engine owns their disposal). It runs the controller-session loop (re-acquires a device after disconnect/bridge death; agent commands go through a catch-all so a failing adapter never kills a loop) and the agent-event loop (pending-approval tracking, haptic routing). Prompts submitted while the agent is busy queue (max 5, optimistic busy flag so double-taps never double-send) and flush when the agent settles — `PromptQueueChanged` reports the count. It raises events on background threads: `LogEmitted`, `ControllerConnected`/`ControllerStatusChanged`, `AgentEventReceived`, `PendingApprovalChanged`. Behavior changes to host loops go here, once.
- `src/CtrlAgent.App` — console host: parses options, builds provider/adapter/profile, wires `HostEngine` events to the console, and runs the interactive command loop. Also owns the `--validate` wizard path.
- `src/CtrlAgent.Gui` — Avalonia desktop app. **Workspace switching**: `App.SwitchWorkspaceAsync` disposes the engine and rebuilds it against a new directory (the adapter reads its cwd when it spawns the CLI, so a live session cannot be moved); `MainViewModel.PrepareForEngineSwap` releases the engine and clears transcript/log/approval state so the previous repository's history never shows under a new one; `WorkspaceWindow` picks from `GuiSettings.RecentWorkspaces` (8 deep, deleted paths pruned) or browses. Reachable from the status-strip workspace chip and the Mainframe settings panel. Otherwise (Fluent dark theme, compiled bindings) on the same `HostEngine`; `MainViewModel` marshals engine events onto the UI thread via `Dispatcher.UIThread.Post`. Tray app: closing the window hides it (`ShutdownMode.OnExplicitShutdown`); tray menu shows/toggles overlay/exits. `ProfileEditorWindow` edits bindings *and layers* and reads top-to-bottom: identity (name + a VALID/HAS ERRORS badge), layers, then list-plus-inspector with Add/Remove docked to the list they act on, then actions with the blocking errors directly above them. Live `ControllerProfileValidator` feedback and applies via `HostEngine.TryApplyProfile` (validated runtime swap that carries pending-approval state over). `OverlayWindow` is the frameless always-on-top HUD sharing `MainViewModel`; `ControllerVisualViewModel` mirrors live input with tri-state brushes (pressed > approval-highlight > idle) and PS/Xbox face labels — the Elite drawing itself is the shared `ControllerMirrorView` UserControl used by the main window and Mainframe (edit the art there, once) — it carries a holo presentation layer: a breathing energy field behind it, targeting brackets and side ticks around it, circuit traces with out-of-phase pulsing nodes on the bare band between the bumpers and the controls, and a slow diagnostic sweep over the shell; `AgentBuddyViewModel` (CTRL·BOT) coaches shortcuts from the live profile — its speech bubble names the exact buttons for the current situation — and clicking the bot pokes it (`Poke()`). **The bot keeps no score**: an XP bar and level badge were removed because they rewarded activity rather than progress and competed with the one line that tells you which button to press; the bot drawing itself is the shared `BotView` UserControl (blush, eye glints, arms/feet, and per-mood whole-body animation) used by both the main window and Mainframe — edit the art there, once. It is presented as a projection: an aura, a cone of light, a fixed orbit ring with a dot that travels it (a rotating canvas flattened by ScaleY, so the dot follows the ellipse rather than a circle), a pulsing pad and rising motes. That layer sits **outside** the rig canvas and is `ClipToBounds`, so it stays planted while the bot hops and nothing escapes into the nameplate. The bot rig carries a `TransformGroup` (scale then translate) with a feet-level `RenderTransformOrigin`, so mood keyframes animate squash-and-stretch and travel together; the ground shadow scales/fades inversely to sell height. Happy plays **once** (two hops → settling sway, `IterationCount="1"` + `FillMode="Forward"`) because a looping celebration stops reading as one; idle/alert/error loop. `GuiSettings` persists options *and UI state* (view toggles, window size/position — saved on hide/shutdown, restored on argless launch; option-only saves preserve stored UI state) to %AppData%/CtrlAgent. The main window extends its client area into the title bar (the command bar is the drag handle). **Hero and status are one card**, two rows — companion + tool rail, then AGENT/WORKSPACE/CONTROLLER facts with the session knobs right-aligned; the wordmark, the session uuid and the PROFILE block were dropped from it (the wordmark told you nothing you did not know, a uuid is furniture, and the profile now rides in the tool rail with its validity dot) which bought ~90px for the conversation. Review/New session moved into the tool rail, **Interrupt appears only while a turn is live**, and Submit is the single primary. The tool-rail ◱ button opens the **diff review panel** — a fullscreen overlay of the workspace's pending changes (colored add/remove rows via `DiffRow`, which only picks colors; the content comes from Presentation's `UnifiedDiffParser`/`WorkspaceDiff`) so what is being approved is visible before more of it is approved; "Ask agent to review" inside it sends the old `ReviewChanges` command, the right-stick scroll bindings page it while open (the conversation otherwise, via `MainViewModel.OutputScrollRequested`), Esc closes, and its card is deliberately opaque unlike every other `.card` — code is read, not glanced at. Icon buttons are stroked `Path.icon` geometry, never emoji — emoji render at the platform's mercy and came out as grey blobs headless. Agent states read through `CtrlAgent.Presentation.AgentStateText` so the UI never prints `ApprovalRequired`; the ACTIVITY card toggles between a Claude-app-style conversation (`ChatMessage` rows; the folding rules live in `CtrlAgent.Presentation.TranscriptFolder`) and the severity-tinted `LogEntry` event stream (controller-input filter chip). Both lists **follow new items only while already scrolled to the bottom** (`MainWindow.StickToBottom`) so reading history is not undone by the next event. The prompt box is multi-line: Enter submits (a tunneling `KeyDown` handler, because `AcceptsReturn` makes the TextBox consume Enter before a bubbling handler or KeyBinding sees it), Shift+Enter inserts a newline, and sending clears the box. Chat bubbles render markdown via `MarkdownView` (backed by Presentation's `MarkdownLite`). A **recents sidebar** lists the workspace's Claude Code sessions from the on-disk store (`ClaudeSessionCatalog`) and a click resumes that exact session through the `ResumeSession` command (Claude restarts with `--resume <id>`, Codex issues `thread/resume`, mock jumps its counter); it shows only for adapters with a readable store, so it hides for mock/codex. A status-strip knob cluster (mode/model/effort/compact, `Button.knob`) and the matching Mainframe tiles read their labels from `HostEngine.Settings` rather than a local index, so a controller binding that changes any of them moves the label too; binding rows (`BindingRow`) and CTRL·BOT share chord shorthand via `ControlLabels`; status dots and bot eyes animate via style classes (`Ellipse.pulse`, keyframe animations). **Mainframe mode** (`MainframeWindow`/`MainframeViewModel`) is the Steam-style fullscreen controller-first UI — entered via the header rail, F11, the **Xbox/PS button**, or double-pressing View. Guide-button support is per-transport and now reported as a capability (`ControllerCapabilities.HasGuideButton`), so a profile that binds it is only advertised on hardware that delivers it: raw-HID DualSense always reports the PS button, XInput reports the Xbox button only through the undocumented ordinal-100 entry point (`XInputGetStateEx`, probed once with a silent fallback), and the GameInput bridge delivers it when the device advertises `GameInputSystemButtonGuide` and the app asked for `GameInputEnableBackgroundGuideButton` — it is **not** reserved by the SDK, it simply has to be requested. Steam and the Xbox Game Bar still hook it globally, so a press may be consumed before it reaches us — View double-press stays as the shortcut that works on every transport; it opens with a staged one-shot boot sequence (CRT strike → grid/bloom field → corner brackets → badge landing with overshoot → three staggered rings → tagline → ONLINE status and fill rail → dissolve, ~3.2s; `BootChime` is a WAV synthesized in memory and played via winmm — no audio asset). Delayed animations set their pre-animation value in markup, because Avalonia renders an element's own value during `Animation.Delay`; agent actions are never navigable — submit/interrupt/review/approve/decline all fire from the user's own profile bindings exactly as outside the mode, and the screen renders them as a read-only HUD that is **contextual** — only bindings that can fire right now appear (`ActionHint`/`RebuildHints`: approval-gated bindings need a pending request, Interrupt needs a live turn, and while a request is pending nothing but the approval answers is shown), bindings sharing a command **and its text** merge into one row (`P1 · RB+A`) — `ControlLabels.Describe` keeps preset-prompt bindings distinct, so A and LB+A never collapse into one entry, and the whole set goes large and amber-pulsing under an "APPROVAL REQUIRED — ANSWER WITH" heading. Focus navigation exists only for the settings panel (permission mode, model, effort, compact, workspace, controller profile, all-shortcuts screen, exit), opened with View or the header button. `SetInputCapture` follows that rule: on while settings/shortcuts/voice own the screen so the d-pad moves focus instead of switching sessions, off the rest of the time so every binding stays live. Voice, file-attachment and output-paging are **bindable commands** (`StartVoicePrompt`, `AttachFile`, `ScrollOutputUp`/`ScrollOutputDown`) that `HostEngine` intercepts before they reach an adapter and re-raises as `VoicePromptRequested`/`AttachFileRequested` — a mic and a file picker are UI, not agent operations. The default profile binds **Y** to voice and **LB+X** to attach, so both work in the main window too rather than only inside Mainframe; when Mainframe owns the screen the app routes dictation to its large overlay, otherwise dictation appends into the prompt box. **Right stick pages the Mainframe agent feed** (80% of the viewport per flick, feed depth 60) and is allowed while input is captured alongside the approval family — opening the settings panel must not freeze text you are part-way through reading. Attachments are paths (not contents) that ride along with the next prompt via `CtrlAgent.Presentation.PromptComposer` — sending them alone would burn a turn, and every agent here can read files itself. `SpeechToTextService` is System.Speech dictation, Windows-only with a graceful "unavailable" elsewhere. Settings tiles respond to hover and click as well as the d-pad, and the window wears a code-drawn reticle cursor (`MainframeCursor`, built with `RenderTargetBitmap` — no .cur asset, falls back to the system cursor if the backend refuses it); CTRL·BOT is center-stage above the live controller mirror, next to the agent-feed panel showing live responses; keyboard fallback (arrows/Enter/Esc/F1/F2) for padless testing. Avalonia is pinned to the last 11.x (11.3.18).

### Cross-adapter invariants

- **An interrupt reports as `AgentInterrupt.State` / `AgentInterrupt.Message` (Core), never a per-adapter choice.** All three adapters disagreed once — Claude said `Completed`, Codex and the mock said `Idle` — and `Idle` routes to *no* pattern, so the same button buzzed on one agent and was silent on another. Interrupting is when you are least likely to be looking at the screen.
- `AgentStateKind.Idle` means "stop haptics"; never route an outcome the user must feel through it.

### Mapping and approval safety

These invariants are tested and must hold:

- `MappingEngine.Process` drops bindings in inactive layers, picks structural matches, keeps only bindings with the **highest modifier count** (chords beat plain buttons), and only then filters by eligibility. Ordering matters: an ineligible approval chord (e.g. RB+A with no pending approval) must produce *no* command rather than falling through to the plain-button action.
- Profile layers activate on device capability (`always` / `requiresPaddles` / `withoutPaddles`); `HostEngine` calls `SetDeviceCapabilities` on every controller connect and carries the capabilities into runtime profile swaps. With no device known, every layer is active. Collision validation runs per capability "world", so a `requiresPaddles` and a `withoutPaddles` layer may share chords but base bindings collide with every layer.
- Bindings with `RequiresPendingApproval: true` fire only while an approval request is pending (`SetPendingApproval`, driven by the app's agent loop). Approval commands are hydrated with the pending session/request ids.
- Default profile: paddles map to approve-once / approve-for-session / decline / cancel; RB+A/Y/X/B are the XInput fallback chords. No default mapping may approve a destructive action with a single accidental face-button press.
- `AxisThreshold`'s `MinimumValue` is **signed** — negative means the negative half of the axis, so stick-up and stick-down are separately bindable (they were not: both sides compared `Math.Abs`, so one binding fired in both directions and the default profile's right-stick scroll pair was impossible to express). Collision detection treats opposite directions on one control as distinct. Gestures (`InputGesture`: Press, Release, AxisThreshold, Tap, Hold, DoublePress) resolve **from event timestamps**, never wall-clock reads — tap/hold split on release duration, double-press on press-to-press interval — so tests can drive them with explicit `DateTimeOffset`s. `MappingEngine`'s constructor runs `ControllerProfileValidator` and throws on any error; validation rejects duplicate/ambiguous chords (Press mixed with Tap/Hold/DoublePress, Tap with DoublePress) and enforces approval safety (approve/decline need `requiresPendingApproval`; approvals must sit on a paddle, chord, or hold).
- Profiles persist as versioned JSON via `ControllerProfileJson` (`--profile` / `--export-profile` in the app); deserialization validates and throws `FormatException` listing every problem.

### Haptics

`HapticScheduler` serializes playback per controller: `PlayAsync` cancels and drains the previous cue, then returns immediately after scheduling the new one (looping cues like `ApprovalRequired` must not block the agent event loop). Patterns are frame lists (`RumbleFrame`: low/high motor + left/right trigger, clamped 0..1). `AgentStateKind.Idle` stops haptics rather than routing a pattern. The app talks to haptics through `HapticSchedulerHub` (Core), which routes to the scheduler of the currently attached controller — detached = no-op, device-loss exceptions swallowed — so the agent loop survives controller swaps. Device implementations must zero rumble in a `finally` when playback ends or the device is disposed.

## Verifying the GUI

The GUI targets `net10.0-windows`, so it cannot be launched on CI or a Linux box and "it builds" proves very little about layout. `tools/CtrlAgent.UiRender` compiles the *same* XAML and view models against a cross-platform TFM and renders every surface to PNG with Avalonia's headless Skia backend:

```bash
dotnet run --project tools/CtrlAgent.UiRender/CtrlAgent.UiRender.csproj -c Release   # PNGs land in ./shots
```

It renders a button matrix (`17-buttons.png`, rest/hover/disabled with pseudo-classes forced) and measures the press state of every variant (`CheckPressDarkens` — a press must be darker than hover; `approve`/`deny` had drifted to getting *brighter* under the finger). It renders the Mainframe boot sequence at five points on its timeline (`20-`…`24-boot-*.png`) — the animation clock advances in headless, so those are real frames. **Run it and look at the output after any XAML change** — it catches what the compiler cannot (a card squeezed to nothing, controls drawn over each other, an empty panel). It also asserts: every visible `Border.card` must have non-zero bounds, land inside the window, and not be fully transparent (a delayed entry animation leaves cards laid out but invisible, which geometry checks pass), and a surface that renders no frame is a failure, so the harness exits nonzero and the `ui-render` CI job fails. `16-main-narrow.png` renders at the window's declared minimum size, where overflow bugs show up first. The harness is deliberately **not** in `CtrlAgent.sln` (like the native bridge), so only that CI job compiles it.

Binding paths are compile-checked (`AvaloniaUseCompiledBindingsByDefault`), so a typo in a `{Binding}` fails the build rather than silently rendering blank.

## Caveats

- The XInput interop, bridge process, and Codex process management are Windows-specific at runtime; the managed solution compiles on any OS, so CI-on-Windows is the real verification.
- Haptic pattern values still await a real-device tuning pass; don't treat the catalog values as final. First Elite hardware findings (2026-07-24) are in `docs/controller-validation.md`: no paddles from the PC GameInput redistributable, no Bluetooth enumeration (XInput covers it), input gated on window focus.
